# flowstate v2 — Global Self-Contained App Design

**Date:** 2026-07-22
**Status:** Approved (supersedes the two-component v1 design for the app; the v1 Python analyzer is demoted to a dev tool)

## What

A single Android APK, distributed via GitHub releases, that anyone can install: log into YouTube Music in-app, play your playlists ad-free with background playback, and get vibe-aware shuffle powered by an ML analyzer that runs entirely on the phone. No PC, no server, no setup.

## Product decisions (locked with user)

- Distribution: GitHub releases APK only (sideload). No Play Store. User handles publishing.
- Playlist-based: vibe shuffle is scoped to the playlist being played (or all-library scope).
- On-device analysis (option "1b"): TFLite models bundled in the APK analyze songs on the phone. No community DB requirement, no Mac dependency for users. The v1 Python analyzer remains ONLY as a dev tool (model conversion + golden parity fixtures) and ships nowhere.
- Analysis is prefetch-capable and cached forever: analyze on first play + background prefetch of likely-next songs + user-triggered batch "Analyze playlist". Results persist in SQLite; a song is analyzed once per model_version.
- Variety guarantee: next-song selection is weighted random sampling over a candidate pool — never argmax. Same song must not deterministically follow the same predecessor.
- Manual feedback: a "doesn't fit" button on the player records negative feedback (pair + song level, decaying) that reshapes future pick weights. No "like" button.
- BPM/key detection dropped in v2 (heavy, cosmetic). Energy kept (cheap RMS).

## Architecture

One React Native (0.86) Android app, four subsystems:

1. **Auth**: WebView login to music.youtube.com; cookies read from the app's CookieManager, stored on-device, injected into the youtubei.js session. Logout = clear cookies + session.
2. **Library sync**: authenticated youtubei.js fetches the user's playlists and their tracks (metadata only: videoId, title, artist, duration). Stored in app-owned SQLite (op-sqlite). Pull-to-refresh + sync-on-open.
3. **On-device analyzer**:
   - Audio: existing stream resolver fetches the m4a to cache (analysis-only download; deleted after).
   - Native module (Kotlin): MediaCodec decode → PCM float mono 16 kHz, middle 120 s.
   - Native/Kotlin mel-spectrogram matched EXACTLY to essentia's TensorflowInputMusiCNN recipe (frame 512, hop 256, 96 mel bands, log compression) — parity-tested against golden fixtures generated by the v1 essentia pipeline (cosine ≥ 0.99 embedding parity gate).
   - TFLite (react-native-fast-tflite or equivalent JSI lib): MusiCNN embedding graph (200-d mean-pooled) + 7 mood heads (per-head positive-class index mapping carried over from v1 — sad/relaxed/party = index 1).
   - Scheduling: lazy (currently playing song), prefetch (top-N likely next candidates), batch (foreground service + progress notification, resumable, charging/wifi-preferred setting).
   - features table: video_id, embedding BLOB float32[200] LE, 7 mood REALs, energy REAL, analyzed_at, model_version. Re-analysis triggered when model_version changes.
4. **Vibe engine + feedback (pure TS)**:
   - Candidate pool: cosine similarity vs center (lock = seed song, drift = last played) above threshold (lock ~0.75, drift ~0.65), mood-chip filter, minus session bans.
   - Weight = sim^4 × recency × feedbackBias; recency = min(1,(songsSince/25)^2).
   - Pick = weighted random sampling.
   - Feedback tables: feedback_pair(from_id, rejected_id, count, last_at), feedback_song(rejected_id, count, last_at). Bias: pair hit ×0.1^decayedCount; song strikes ×0.5^decayedCount; neighborhood haircut ×0.6 when sim(candidate, struck)>0.9 and sim(center, struck_from)>0.8. Decay: count × 0.5^(days/30).
   - Pool-empty fallback: relax threshold once, then playlist-random with a visible notice.

## Data model (app-owned SQLite, schema_version "2")

songs(video_id PK, title, artist, duration_s), playlists(playlist_id PK, name, kind), playlist_songs(playlist_id, video_id, position), features(video_id PK, embedding, mood_happy..party, energy, analyzed_at, model_version), feedback_pair, feedback_song, meta(key,value: schema_version, model_version, account tag).

## UX flow

Login → playlists list (analyzed-count badge per playlist) → playlist screen (play, shuffle-by-vibe, "Analyze all") → player (play/pause/next/prev, lock/drift toggle, mood chips, "doesn't fit" button, analysis indicator) → settings (re-sync, analysis prefs, logout, about/version).
Unanalyzed songs: playable always, excluded from vibe recommendations until analyzed; plain-random fallback with "building vibe map N/M" indicator when pool insufficient.

## Delivery plans

- **Plan B2 — vibe engine + feedback (pure TS)**: engine module + feedback store + wire into player controller as VibeQueue (QueueSource). Testable immediately against v1 vibes.db import path (998 analyzed songs already on the dev phone).
- **Plan C — in-app login + on-device library sync**: WebView auth, authenticated youtubei.js library fetch, schema v2 migration, remove file-import as primary path (keep as debug).
- **Plan D — on-device analyzer**: offline model conversion (pb → tflite, dev-tool task), Kotlin decode+mel native module, TFLite integration, golden-fixture parity tests, lazy/prefetch/batch scheduling.
- **Plan E — release**: screens polish, signed release APK, README for end users, GitHub release workflow.

Each plan lands as working, testable software; the app is usable after every plan.

## Risks

- Mel-spectrogram parity is the hard engineering (Plan D); gated by fixtures before any release.
- youtubei.js authenticated library APIs less battle-tested than anonymous ones; YouTube changes can break login/sync/stream — accepted (sideload FOSS reality), fixed by dependency bumps.
- TFLite conversion of TF1-era frozen graphs: one-time dev task, validated offline before app work starts.

## Explicitly out of scope (v2)

iOS; Play Store; server infrastructure; model retraining on device; BPM/key; likes/implicit-skip signals (candidate for v3).
